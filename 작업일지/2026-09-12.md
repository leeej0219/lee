### 판단 및 결정
- Firebase 프로젝트 생성은 사용자 본인의 구글 계정 인증이 필요한 절차라 대신 수행할 수 없고, GitHub Pages 활성화도 보유한 GitHub 도구로는 저장소 설정을 바꿀 권한이 없어 대신할 수 없음을 사용자에게 설명.
- 사용자 부담을 최소화하기 위해 백엔드를 **Firebase(가입 필요) → jsonblob.com(가입 전혀 불필요, 익명 JSON 저장소)** 로 전면 교체하기로 결정. (이전에 사용자가 "가입 없는 익명 저장 서비스"보다 "Firebase"를 선호했던 결정을 상황 변화로 인해 번복함 — 대신 안정성이 약간 낮아질 수 있음을 사용자에게 고지.)
- "볼트 코드" 개념은 유지하되, 무작위로 직접 생성하던 코드 대신 jsonblob이 발급하는 블롭 ID를 볼트 코드로 사용하도록 변경.

### 남은 이슈 / 한계 (사용자에게 고지 필요)
- jsonblob.com은 문서 단위가 아니라 볼트 전체를 하나의 JSON으로 저장하므로, **두 기기에서 동시에 서로 다른 메모를 편집**하면 나중에 저장한 기기가 이전 기기의 변경을 덮어쓸 수 있음(평소처럼 한 기기씩 쓰면 문제없음).
- 이 세션은 네트워크 정책상 gstatic.com, jsonblob.com 등 외부 도메인에 대한 연결 테스트(curl)를 직접 할 수 없었음 — 실제 사용자 브라우저에서의 동작 여부는 배포 후 확인 필요. jsonblob의 CORS 지원(특히 생성 시 `Location` 헤더 노출 여부)에 대한 확신은 기존 지식에 근거한 것으로, 실패 시 대안 서비스로 교체 필요.
- 여전히 남은 사용자 작업은 GitHub 저장소 Settings > Pages에서 `main`/`docs` 소스 켜기 한 가지뿐 (Firebase 관련 가입/설정은 모두 제거됨).

### 진행 상황

### 새로 발견된 문제: jsonblob.com 연동 실패
- "새 볼트 만들기"를 눌렀을 때 "볼트를 만들지 못했어요" 오류 발생.
- 원인 추정: jsonblob.com이 블롭 생성 시 새 ID를 응답의 `Location` 헤더로만 알려주는데, 이 헤더가 브라우저의 CORS 정책상 기본적으로 JS에 노출되지 않는 헤더라서(서버가 `Access-Control-Expose-Headers: Location`을 명시적으로 보내지 않으면) 코드가 새로 만든 볼트의 ID를 읽지 못해 실패한 것으로 보임 — 사전에 고지했던 바로 그 위험이 실제로 발생.
- 이 세션은 이번에도 jsonblob.com/kvdb.io에 curl로 직접 접근이 막혀 있어(조직 네트워크 정책) 서비스 자체를 이 자리에서 검증할 수는 없었음.

### 대응: kvdb.io로 재교체
- `docs/index.html`의 저장 계층을 jsonblob.com → **kvdb.io**로 교체.
- 핵심 차이: kvdb.io는 별도의 "생성" API 없이 임의의 버킷 이름(볼트 코드)에 바로 GET/PUT 하면 자동으로 생겨서, 응답 헤더를 읽을 필요가 전혀 없음 — 이전 실패의 근본 원인(헤더 노출 문제)을 구조적으로 제거함.
- 볼트 코드는 다시 클라이언트가 무작위로 생성(12자리, 헷갈리는 0/O/1/I 제외)하는 방식으로 복귀.
- 실패 시 원인 파악을 돕기 위해 각 오류를 `console.error`로도 남기도록 추가.

### 남은 이슈
- kvdb.io 역시 이 세션에서 직접 검증하지 못했음 — 사용자가 실제 배포된 사이트에서 다시 테스트 필요. 이번에도 안 되면 브라우저 개발자 도구(F12) 콘솔에 찍힌 정확한 오류 메시지를 확인해야 다음 원인을 좁힐 수 있음.
